# HSCrm 1.0.0 - Windows Server / IIS deployment

This document describes the release layout and the required configuration. It does not perform a deployment.

## Persistent directory layout

Keep versioned application files separate from persistent data:

- `D:\\HSCrm\\Releases\\Backend\\1.0.0`
- `D:\\HSCrm\\Releases\\Dashboard\\1.0.0`
- `D:\\HSCrm\\Shared\\UserImages`
- `D:\\HSCrm\\Shared\\DataProtectionKeys`
- `D:\\HSCrm\\Backups\\Database`

Use a new version directory for every release. Do not extract a new build over the currently active release directory.

## Backend environment

Set these values in the Backend IIS application environment (or a protected external configuration source):

- `ASPNETCORE_ENVIRONMENT=Production`
- `ConnectionStrings__HSCrmConnectionString` = production SQL Server connection string
- `Jwt__Key` = strong, unique secret (never commit it)
- `Jwt__Issuer` and `Jwt__Audience` = values matching the token validation configuration
- `PublicBaseUrl` = public HTTPS origin of the API, without a path
- `Cors__AllowedOrigins__0` = exact Dashboard HTTPS origin
- `Database__ApplyMigrationsOnStartup=false`
- `Storage__UserImagesPath=D:\\HSCrm\\Shared\\UserImages`

Production startup intentionally does not apply EF migrations automatically. The database must be migrated before starting the new Backend release. Startup seeding still runs and therefore requires the migrated schema and a reachable database.

The upload directory must be outside the versioned release directory. Grant the Backend App Pool identity Modify access to `Shared\\UserImages`; do not grant it broad write access to the application or server.

## Dashboard environment

Set:

- `ASPNETCORE_ENVIRONMENT=Production`
- `ApiAddress` = absolute public HTTPS API base URL ending in `/` (use the API base path expected by the Dashboard, for example `https://api.example.com/api/`)
- `DataProtection__KeysPath=D:\\HSCrm\\Shared\\DataProtectionKeys`

The Dashboard refuses to start in Production if its Data Protection key directory is missing or inside the versioned application directory. Grant the Dashboard App Pool identity Modify access only to this key directory. Keep the same application name (`HSCrm.Dashboard`) and key directory across upgrades so existing authentication cookies remain decryptable.

Protect the shared key directory with restrictive NTFS ACLs and include it in the server backup policy. The Dashboard release branch applies machine-level Windows DPAPI protection to persisted keys when running on Windows. If the Dashboard is hosted on another operating system, configure an equivalent certificate-based key protector before Production.

## IIS prerequisites

- Install the .NET 8 Hosting Bundle matching the server architecture and keep it patched.
- Use separate IIS sites/application pools for Backend and Dashboard.
- Set each application pool to **No Managed Code**.
- Run each pool under a dedicated identity with only the required directory permissions.
- Bind valid HTTPS certificates to both public host names; Dashboard cookies are configured as Secure and HttpOnly.

## Release sequence

1. Take and verify a SQL Server backup. Keep the current release directory intact.
2. Download the Backend, Dashboard, and database migration artifacts from the same release workflow/tag. Verify their `release-info.txt` commit and version metadata.
3. Review the generated `HSCrm-Database-Idempotent.sql` and apply it to the intended database using an approved SQL deployment identity. The script is idempotent, but it is not a substitute for a backup or a reviewed change window.
4. Extract each publish artifact into its new version directory and verify the environment configuration and NTFS permissions.
5. Switch the IIS application physical paths to the new version directories and recycle the respective application pools.
6. Verify `/health/live` and `/health/ready` on the Backend, and `/health/live` on the Dashboard. Then smoke-test login, tenant isolation, user-image upload/display, and a representative read/write workflow.
7. If application validation fails, switch IIS back to the previous application directories. Database rollback is a separate operation: restore the pre-release backup unless a reviewed, tested reverse migration is explicitly approved.

## Current limitations

- The release workflows generate packages only when manually dispatched or when a matching version tag is pushed. No package or production deployment is created merely by merging a pull request.
- The migration script is generated by EF Core tooling without starting the API host or running its seed routine.
- Database migration execution, IIS path switching, backup, and rollback remain operator-controlled steps.
- Verify the actual Dashboard API base path and production environment variables against the deployed IIS bindings before the first release.
